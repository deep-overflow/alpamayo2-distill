# Plan: detection 라벨을 투영 GT 박스로 교체 (카메라 vs 카메라 + LiDAR 재비교)

- 작성 2026-10-21 · 상태: **승인됨 (2026-10-22) → 중단 (2026-10-22)**: 기대 효과가 작다고 판단해 train 라벨 단계에서 멈춤. val/ood/dev 라벨과 v2 기준 박스, 학습 코드 옵션(`--det-source gt`)은 남김
- 이전 결과: `reports/2026-10-20_a2-distill-lidar.md`. A2 라벨로 학습했을 때 LiDAR 입력의 이득이 없었다.
- branch(승인 후 생성): `a2-distill-gtdet`. 먼저 `a2-distill-lidar`의 LiDAR 작업(코드, 계획, 보고서)을 커밋한다.
- 코드 위치: `experiments/distill/` (A2 `src/`는 수정하지 않음)

## 1. 목적

- **가설**: detection 라벨이 실제 3D 박스이면 LiDAR 입력이 detection을 개선한다. 특히 먼 물체의 recall과 위치 정확도(IoU 0.5)가 좋아질 것이다.
- 이전 실험에서는 detection 라벨이 카메라만 본 A2의 출력이었다. 그래서 LiDAR가 정답을 더 잘 알아도 손실이 줄지 않았다.
- **비교**: GT 라벨로 다시 학습한 카메라 student와 LiDAR student. 둘 사이에는 입력 외의 차이가 없다.

## 2. 확정된 결정 (2026-10-21 Q&A)

| # | 항목 | 결정 |
|---|---|---|
| G1 | detection 라벨 | **투영 GT만** 쓴다. A2 detection 라벨은 쓰지 않는다. 정답 분포가 없으므로 det의 KL 손실은 빼고 CE만 남긴다 |
| G2 | 가려진 물체 | **LiDAR 점 수로 거른다.** 3D 박스 안의 LiDAR 점이 k개 미만이면 제외한다. 평가 기준 박스에도 같은 규칙을 쓰고, 기존 규칙의 결과도 함께 보고한다 |
| G3 | 학습 | 카메라 student와 LiDAR student를 **둘 다** GT 라벨로 다시 학습한다. GPU 0–3에서 차례로 돌린다 |

**나머지는 이전 실험과 같다**
- 시작점 `s2_wide/init`, train 10k, driving 과제(A2 CoC 라벨 + GT 궤적 flow).
- 학습 일정: 최대 10 epoch, lr 1e-4, warmup 100, global batch 32, patience 5.
- RangeViT 구조와 LiDAR 캐시도 그대로다.

## 3. 확인한 사실 (2026-10-21)

**3D 라벨의 출처** (2026-10-22 확인)
- PhysicalAI-AV 공식 feature `labels/obstacle.offline`이다. 데이터셋 버전 26.03에서 추가됐고, 전체 clip의 97%에 있다.
- 사람이 단 라벨이 아니다. README는 "autogenerated (non-GT) machine labels"라고 쓰고, 행마다 `source = scene:obstacles:autolabels:v2`가 붙어 있다.
- 필드: track_id, cuboid(중심, 크기, quaternion), label_class.
- 좌표계: `reference_frame = rig`, `reference_frame_timestamp_us = timestamp_us`. 즉 각 시각의 rig 좌표계이고, 투영 코드도 이를 따른다.
- 이 문서에서 "GT"는 이 자동 라벨을 가리킨다.
- `obstacle_perclip/`은 `build_cache_distill.py`가 Hub에서 clip별로 뽑아 둔 사본이다.

**3D 라벨 범위**
- `obstacle_perclip` 라벨이 train 10,000 / dev 232 / val 482 / ood 240 clip에 있다.
- 이는 LiDAR가 있는 clip과 정확히 같다. 따라서 두 student 모두 이 clip 집합에서 학습하고 평가한다.

**기존 투영 코드** (`project_obstacles.py`, G0c 통과)
- front-wide t0 frame의 시각으로 track을 보간하고 f-theta로 투영한다. 결과는 cuboid 8개 꼭짓점을 감싼 사각형이다.
- 단위는 Qwen 0–1000이다.
- 기존 필터: 가시율 ≥ 0.5, 높이 ≥ 12 px@320, 거리 ≤ 80 m. 가림 검사는 없다.
- val 기준으로 투영된 7,916개 중 2,296개를 남긴다(clip당 평균 5.3개, 최대 72개).
- 클래스 구성은 vehicle 1,801, pedestrian 460, cyclist 23, other 12다.

**A2 출력 형식**
- `[{"bbox_2d": [x1, y1, x2, y2], "label": "Car"}, ...]<|im_end|>` 형태다.
- 박스 하나가 약 32 토큰이다(숫자가 한 자리씩 토큰이 됨).
- train 라벨은 clip당 평균 2.2개, 최대 14개, 최대 451 토큰이다.
- 박스 순서에는 일정한 규칙이 없다(3개 이상인 경우 중 x1 오름차순이 21%).
- 질문은 "Find all vehicles, pedestrians and cyclists visible in the Front camera ..."이다.

**student vocab** (V′ 4,885)
- 포함됨: `Car`, `Truck`, `Bus`, `Trailer`, `Tram`, `Pedestrian`, `Cyclist`, `Bike with rider`.
- 빠짐: `Vehicle`, `Person`, `Stroller`, `Animal`, `Other`.

## 4. 설계

### 4.1 GT 박스와 LiDAR 가시성 (`gt_det_labels.py`, 새 파일)

세트: train_10k, dev_238, val_500, ood_262 (LiDAR clip 약 11k).

1. **투영**: `project_obstacles.project_sample`을 그대로 쓴다. 기존 필터와 `keep` 플래그도 유지한다.

2. **LiDAR 점 복원**: 캐시한 range image(128×1024)에서 유효 칸마다 점 하나를 rig@t0 좌표로 되살린다.
   - 거리 r(센서 기준)과 높이 z(rig)는 range image 채널에서 읽는다.
   - 방위각 φ는 열 중심값을 쓴다(rig@t0 기준).
   - 수평 거리 ρ는 `|(ρcosφ, ρsinφ, z) − t_lidar| = r`을 풀어 구한다. t_lidar는 `sensor_extrinsics`의 LiDAR 위치다.
   - 원본 대비 점 수는 약 37%(유효 칸 약 11만 개 / 원본 30만 점)다. 방위 해상도는 0.35°다.

3. **시간 보정**
   - LiDAR 점은 카메라 frame보다 0–200 ms 오래됐다. 20 m/s로 움직이는 차는 최대 4 m 이동한다. 그대로 세면 움직이는 물체가 잘못 제외된다.
   - 그래서 박스마다 다음을 한다.
     - 박스 방위의 측정 시각(t0 − `dt_col`)으로 track cuboid를 보간한다.
     - egomotion으로 그 cuboid를 rig@t0로 옮긴다(`build_lidar_distill.deskew`와 같은 계산).

4. **점 세기**
   - cuboid를 수평으로 0.2 m 키운다.
   - 바닥 0.2 m 위쪽만 센다. 박스 아래 지면 점이 섞이지 않게 하기 위해서다.
   - 결과는 `n_lidar`로 저장한다.

5. **새 규칙** `keep_v2`: 아래 셋을 모두 만족하는 박스만 남긴다.
   - 기존 `keep`
   - `n_lidar ≥ k` (기본값 k = 3)
   - 클래스가 vehicle, pedestrian, cyclist 중 하나 (질문에 맞춤. protruding_object와 animal은 제외)

6. 저장: `outputs/distill_gtboxes/<set>.parquet`(박스별 `n_lidar`, `keep`, `keep_v2`)와 `<set>_stats.json`.

### 4.2 GT detection 라벨 시퀀스

**텍스트**: A2와 같은 JSON 형식으로 쓴다. 좌표는 정수로 반올림한다.

**클래스 이름**: student vocab 안에 있는 A2 스타일 이름만 쓴다.

| GT 클래스 | 이름 |
|---|---|
| automobile, other_vehicle | Car (`Vehicle`은 vocab 밖) |
| heavy_truck | Truck |
| bus | Bus |
| trailer | Trailer |
| train_or_tram_car | Tram |
| person, stroller | Pedestrian |
| rider | Cyclist |

**순서와 상한**
- 가까운 순서(rig 평면 거리)로 정렬하고, 최대 40개(약 1,300 토큰)까지만 쓴다.
- 상한에 걸리는 clip 비율은 게이트에서 보고한다.
- 박스가 없으면 `[]`로 쓴다.

**저장**: teacher 라벨과 같은 형식의 npz(`gen_ids`, `text`)를 `outputs/distill_gtdet/<set>/det/`에 저장한다. top-k 필드는 없다.

### 4.3 학습 코드 변경 (최소)

- `distill_data.DistillDataset(..., det_source="a2" | "gt")`
  - `gt`이면 det 라벨을 `distill_gtdet`에서 읽는다.
  - 이때 `kd_ids`와 `kd_p`는 넣지 않는다.
- `train_student.Step.seq_losses`: `kd_ids`가 없으면 KL을 0으로 둔다.
- `train_student.py --det-source gt`
  - 이 옵션은 config.json에 기록된다.
  - dev 손실의 det 부분은 GT에 대한 CE가 된다.
- dev 평가 노이즈 고정은 두 실행 모두에 적용한다. 이전 실험에서는 카메라 실행만 무작위 노이즈였는데, 이번에는 두 실행이 같은 dev 232 clip을 같은 조건으로 평가한다.
- `eval_student.py`: det 생성 최대 길이를 512에서 1,400 토큰으로 늘린다.

### 4.4 학습 실행

| 순서 | exp id | 입력 | 예상 시간 |
|---|---|---|---|
| 1 | `distill_s2_wide_gtdet` | 카메라 | 약 10–11 h |
| 2 | `distill_s2_wide_lidar_gtdet` | 카메라 + LiDAR | 약 11 h |

- GPU 0–3, FSDP2를 쓴다.
- 각 실행 전에 20 step smoke로 손실과 메모리를 확인한다.
- det 시퀀스가 길어져 step 시간이 약 10% 늘 수 있다.

### 4.5 평가

**세트와 생성**
- val_500과 ood_262 중 LiDAR가 있는 clip(482, 240)만 쓴다. 두 student 모두 같은 clip이다.
- `eval_student.py`로 생성한다. 설정은 이전과 같다(driving T 0.6, det T 0.1, K 8).

**detection 기준**
- 주 기준: `keep_v2` 박스.
- 보조 기준: 기존 `keep` 박스. 이전 보고서 수치와 비교하기 위해서다.
- 두 기준 모두로 A2와 이전 두 student(A2 라벨로 학습)도 다시 채점한다.

**detection 지표**
- P/R/F1 @IoU 0.5와 0.3.
- 거리별(0–30 / 30–60 / 60+ m), 클래스별 recall.
- clip당 박스 수, 종료율.

**나머지 지표**: 궤적(minADE@1/6/8, minFDE)과 reasoning(A2 대비 meta-action, ROUGE-L)은 이전과 같다. driving 과제는 바뀌지 않았으므로 큰 변화가 없어야 한다.

**paired 비교**: lidar_gt − cam_gt를 clip별로 비교하고 bootstrap 95% CI를 붙인다.
- TP / FP / 기준 박스 수
- 거리 구간별 recall

## 5. 게이트

- **G-GT a (가시성 필터)**
  - LiDAR 필터로 빠지는 박스의 비율을 k = 1, 3, 5별로 보고한다. 거리별과 클래스별로도 나눈다.
  - 시간 보정의 효과를 확인한다. 빠르게 움직이는 track(> 5 m/s)이 보정 전보다 덜 제외되어야 한다.
  - overlay 20장에 남은 박스, LiDAR로 빠진 박스, 기존 필터로 빠진 박스를 다른 선으로 그린다. 눈으로 볼 때 빠진 박스가 실제로 가려진 물체여야 한다.
  - **판단**: k = 3에서 overlay상 "보이는데 빠진" 박스가 거의 없으면 그대로 진행한다. 문제가 있으면 멈추고 보고한다.
- **G-GT b (시퀀스)**
  - 모든 GT 시퀀스가 student vocab 안이어야 한다(`remap` assert).
  - 길이 분포와 40개 상한에 걸리는 clip 비율을 보고한다.
  - GT 텍스트를 `det_utils.parse_boxes`로 다시 읽었을 때 박스가 그대로 복원되어야 한다.
- **G-GT c (smoke)**: 두 student 모두 20 step 동안 NaN이 없고 손실이 줄어야 한다. 메모리 여유도 확인한다.

## 6. 순서와 시간

1. `a2-distill-lidar` 커밋 → `a2-distill-gtdet` branch를 만든다.
2. `gt_det_labels.py`로 4개 세트를 처리한다. CPU 16 worker로 약 1시간이 걸리고, 보정값을 받으려고 Hub에서 일부를 읽는다. 끝나면 게이트 a와 b를 확인한다.
3. 학습 코드를 바꾸고 smoke(게이트 c)를 돌린다.
4. 카메라 GT 학습(약 10–11 h) → LiDAR GT 학습(약 11 h).
5. 두 student를 평가한다(GPU 0–3, 약 1.5–2 h). 이전 모델들은 새 기준으로 다시 채점한다(CPU).
6. 보고서 `reports/YYYY-MM-DD_a2-distill-gt-det.md`.

합계는 약 25–27시간이다.

## 7. 리스크

- **"GT"의 품질**: `obstacle.offline`은 자동 라벨이다(§3). 라벨 오류가 그대로 학습되고 평가 기준에도 들어간다.
  - 자동 라벨러가 어떤 센서를 썼는지는 문서에 없다. 오프라인 라벨러는 보통 LiDAR와 여러 frame을 쓰므로 LiDAR 쪽에 유리한 편향이 있을 수 있다(추정).
- **박스 정의**: cuboid를 감싼 사각형이라 가까운 차에서는 실제로 보이는 영역보다 크다(G0c). 학습과 평가가 같은 정의를 쓰므로 일관성은 있다.
  - 하지만 A2를 이 기준으로 채점하면 불리하다. 보이는 영역에 맞춰 박스를 그리기 때문이다.
- **LiDAR 기준 가시성**: 라벨이 "LiDAR에 잡히는 물체"로 정의된다.
  - 카메라 student도 같은 라벨을 배우지만, 이 정의가 LiDAR student에 약간 유리할 수 있다.
  - 보고서에 이 점을 적고, 기존 규칙으로 잰 결과도 함께 낸다.
- **보행자**: A2 라벨에는 보행자가 거의 없었다(train 표본 864개 중 3개). GT에는 val 기준 20%가 보행자다. det 과제의 난이도가 올라가므로 이전 실험과 det 손실 값을 직접 비교하면 안 된다.
- **dev 손실 구성 변화**: det KL이 빠져 dev 총손실의 크기가 달라진다. 조기 종료 시점도 이전 실험과 다를 수 있다.
- **range image 복원 오차**: 해상도를 낮춘 점이라 먼 작은 물체는 점이 적게 잡힌다. 거리별 제외 비율로 확인한다.
